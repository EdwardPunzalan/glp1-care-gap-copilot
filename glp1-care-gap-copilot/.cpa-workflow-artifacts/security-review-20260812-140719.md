## Detailed Findings

### Plugin API Server Security — N/A

The plugin exposes no callable surface. It registers exactly one `BaseHandler`
that responds to `NOTE_OPENED` and `PATIENT_CHART__MEDICATIONS` and returns a
single `ADD_OR_UPDATE_PROTOCOL_CARD` effect. There is no endpoint to
authenticate, no request to authorize, and no inbound data to validate.

### FHIR API Client Security — N/A

No FHIR client usage. All chart data is read through the Canvas ORM
(`canvas_sdk.v1.data.*`), which is already scoped to the executing instance.
The plugin holds no Canvas API credentials.

The only outbound network call in the plugin is the optional Anthropic LLM
request (see *Third-Party Data Egress*), which carries no chart data.

### Application Scope — N/A

Handler-only plugin. No `scope` declared, and no embedded/portal application, so
there is no patient-facing vs. staff-facing token mismatch to assess.

### Variables Declaration — ✅ Pass

- 14 variables declared in the manifest's modern `variables` array
- 14 variable names read in `config.py`
- **Read but not declared:** none
- **Declared but unused:** none
- Legacy `secrets` array: not used (modern schema only)
- Hardcoded credential scan (JWT, `sk-*`, long base64-like literals): **no matches**

`ANTHROPIC_API_KEY` is the only variable marked `sensitive: true`, which is
correct — the remaining 13 are clinical thresholds and matching lists that
operators need to read back in plaintext to verify.

### Patient Data Scoping — ✅ Pass

Every query touching patient data is constrained to the target patient:

| Location | Query | Scoping |
|---|---|---|
| `cohort.py:58` | `Condition` | `for_patient(patient_id)` |
| `cohort.py:83` | `Medication` | `for_patient(patient_id)` |
| `gaps.py:59` | `Observation` | `for_patient(patient_id)` |
| `gaps.py:76` | `LabValue` | `report__patient__id=patient_id` |
| `gaps.py:95` | `Appointment` | `patient__id=patient_id` |
| `gaps.py:110` | `Appointment` | `patient__id=patient_id` |
| `dedupe.py:27` | `Task` | `patient__id=patient_id` |

`card.py:56` (`LabPartner`) and `card.py:67` (`LabPartnerTest`) are intentionally
**not** patient-scoped. These are instance-level catalog records — the lab
partner directory and its orderable test list — and contain no patient data.
Scoping them to a patient would be meaningless.

The patient id is taken from `self.event.target.id`, i.e. the patient whose
chart Canvas is already rendering. The plugin never widens beyond that, and
never uses `patient_filter` to fan out across patients.

Test coverage backs this: `test_cohort.py` and `test_gaps.py` each assert that
another patient's records do not satisfy the current patient's rules.

### Third-Party Data Egress — ✅ Pass

The Anthropic call is the plugin's only third-party transmission. Two things
are sent, and nothing else:

1. A **static system prompt** (module constant, no interpolation)
2. `json.dumps(build_payload(...))`

`build_payload` is constructed additively from derived scalars — gap type
strings, integer day counts, configured lab *names*, a medication *class*
constant, and a week count. It is not a filtered patient record, so there is no
field that could leak by omission of a redaction step.

Explicitly never transmitted: name, DOB, MRN, patient id, address, contact
info, medication names or doses, raw lab values, note text, provider identity.

`tests/test_rationale.py` enforces this by **allow-list** — any new key added to
the payload fails the suite until it is explicitly declared safe — and
separately asserts the serialized payload contains no identifier-like
substrings. Model output is passed through `sanitize()` (whitespace collapsed,
markdown stripped, length-capped) before rendering into the card.

The path is disabled by default in practice: with no `ANTHROPIC_API_KEY` set,
`llm_available()` is false and no request is made. `ENABLE_LLM_RATIONALE=false`
is an independent kill switch.

### Log Hygiene — ⚠️ 2 LOW

All 10 log statements were reviewed. **None currently emits PHI or a
credential.** The handler's two INFO lines record only booleans and gap-key
lists, with no patient identifier. Two latent risks:

**LOW-1 — Sensitive-value redaction is incidental, not enforced.**
Four of the five config parsers (`_positive_int`, `_optional_int`, `_flag`,
`_csv`) log the raw value on a parse failure. `ANTHROPIC_API_KEY` is safe today
only because it happens to route through `_text()`, the one parser that never
logs. Nothing structurally prevents a future sensitive variable from being
parsed by one of the other four and having its value written to logs.

**LOW-2 — Exception text is logged verbatim on the LLM path.**
`rationale.py:134` logs `{error}` from the LLM call. If the underlying client
ever embeds request or auth detail in an exception message, that text reaches
the logs. Impact is bounded — the payload is PHI-minimal by construction — but
an auth failure carrying key material would be worse than the payload itself.
Not verified to occur with the current SDK; raised as defense-in-depth.

## Recommendations

| Priority | Issue | Location | Recommendation | Status |
|----------|-------|----------|----------------|--------|
| LOW | Sensitive values redacted only by accident of which parser is used | `config.py:80,95,110,138` | Redact structurally by key name so any variable declared `sensitive` is masked regardless of parser | ✅ **RESOLVED** |
| LOW | Raw exception text logged on LLM failure | `rationale.py:134` | Log the exception *type* plus a length-bounded message rather than the full text | ✅ **RESOLVED** |

### Resolution detail

**LOW-1** — Added `SENSITIVE_VARIABLES` and `_loggable()` in `config.py`. All four
logging parsers now render values through `_loggable()`, which masks any variable
named in the sensitive set. Redaction is keyed on the variable name, so it no
longer depends on which parser a variable happens to use.

Three tests enforce it, one of which reads `CANVAS_MANIFEST.json` directly and
asserts that every variable marked `sensitive: true` is covered — so marking a
new variable sensitive without adding it to the redaction set fails the suite.

**LOW-2** — `rationale.py` now logs `type(error).__name__` plus the message
truncated to `MAX_ERROR_CHARS` (200), rather than the full exception text.

Re-verified after fixes: 111 tests pass, 100% statement coverage, `mypy` clean,
`canvas validate` loads the handler cleanly in the RestrictedPython sandbox.

## Verdict

**✅ PASS** — no HIGH or MEDIUM issues.

The plugin has an unusually small attack surface: no endpoints, no inbound
requests, no Canvas API credentials, and read-only patient access that is
patient-scoped everywhere. Its one genuine security-relevant behavior —
transmitting to a third-party LLM — is built so that PHI cannot reach the wire
by construction rather than by filtering, and is enforced by allow-list tests.

The two LOW findings are hardening of paths that are not currently exploitable.
